\begin{abstract}
\noindent This document specifies a \textbf{fully local} benchmark for agent-memory systems --- the storage
and retrieval layer that lets an assistant remember facts about its user across a conversation --- and analyses
\emph{why} different architectures succeed or fail on different kinds of question. Seven systems are evaluated
on a single synthetic user under a uniform, model-controlled protocol with no cloud calls. The instrument is a
\textbf{657-message single-user corpus} (257 canonical facts buried under 400 distractors) probed by
\textbf{460 questions across eight capability classes}. The document's purpose is twofold: (1) to define the
\textbf{taxonomy} --- what each question class tests, why it matters, how it is scored, with worked examples
--- so that a score is interpretable as a specific memory capability; and (2) to explain the
\textbf{per-category results mechanistically} --- why graph structure wins complete-set and multi-hop queries,
why raw-text retrieval wins single-hop and temporal queries, and why their \textbf{union} (CI-Server's hybrid
configuration, \textbf{91.1\%}, field-best) dominates by inheriting both. A recurring theme: headline accuracy
hides the real story, which lives in the per-category profile.
\end{abstract}

\section{Purpose and scope}

An agent-memory system ingests a stream of user statements and later answers questions about them. Two systems
with identical headline accuracy can have completely different competence profiles --- one reliably returns
complete sets but fumbles single facts, another the reverse. This benchmark is built to \textbf{expose those
profiles}, not just rank systems. Every design choice serves that goal: a fixed, shared answerer so we measure
the \emph{memory layer} and not the writer; a taxonomy whose classes map to distinct retrieval mechanisms; and
two scored dimensions (was the fact \emph{retrieved}; was it \emph{answered}) whose gap is itself diagnostic.

The constraint throughout is \textbf{local-only}: no cloud APIs, no hosted SaaS. Every model runs on-device.
This excludes cloud-only providers (Honcho, RetainDB, Supermemory, Memori) and forces self-hosted
configurations of the rest --- e.g.\ Mem0 as its open-source library over a local vector store, not its hosted
service.

\section{Benchmark design}

\subsection{One user is the only real use case}\label{sec:single-user}
Each system under test is built for a \emph{single deployment serving a single user}; none has a first-class
notion of separate accounts inside one store. This is not incidental --- it is the production use case for a
personal assistant. An early design modelled three \emph{independent} users in one store; it was abandoned
because it measured identity-handling artifacts that never arise in deployment (a consolidation store would
bind one user's first-person facts to another user's named entity; a graph store would mis-anchor them to its
canonical ``self'' node). The definitive corpus therefore models \textbf{one user, ``Max,'' plus a rich
network of people he knows}: two friends (Priya, Jordan) and their families and colleagues are folded in as
third-party facts that Max states. This keeps the benchmark realistic \emph{and} naturally generates deep
relational and multi-hop structure (Max $\to$ friend $\to$ their relative $\to$ attribute).

\subsection{Two-phase, model-controlled protocol}
Every system runs in its own container exposing a uniform HTTP contract (\texttt{reset}, \texttt{ingest},
\texttt{flush}, \texttt{retrieve}, \texttt{answer}); the orchestrator speaks only this contract, so each system
is a black box behind the same interface.

\begin{itemize}[nosep]
  \item \textbf{Phase A --- ingest \& extraction.} Every system ingests the identical corpus using the same
  extractor LLM (\texttt{gemma-4-31b-it-abliterated}) and the same embedding model
  (\texttt{nomic-embed-text}).\footnote{Two flagged exceptions: Hindsight uses its built-in
  \texttt{bge-small} embedder; Holographic uses \emph{no} LLM and \emph{no} embeddings (keyword + algebraic
  binding). Both are noted at the relevant rows.}
  \item \textbf{Phase B --- answer \& judge.} A \emph{single, constant} retrieval-augmented answerer and LLM
  judge (\texttt{ornstein-3.6-27b}) serves \emph{all} systems. Given a question, each system retrieves its own
  context; that context is handed to the \emph{same} answerer; the answer is graded by the \emph{same} judge.
  We thus compare memory layers, holding the reader/writer constant.
\end{itemize}

\subsection{Two scored dimensions}
Each question yields two measurements:
\begin{itemize}[nosep]
  \item \textbf{Answer} --- did the constant answerer, given the system's retrieved context, produce the
  correct final answer? (the headline metric.)
  \item \textbf{Storage} --- was the gold fact actually \emph{present in the raw retrieved context}, regardless
  of whether the answer was right?
\end{itemize}
The \textbf{gap between them is diagnostic}. High storage with lower answer means the fact was retrieved but
buried in noise or ambiguity (a \emph{precision} problem). Low storage means the fact was never surfaced (a
\emph{recall} problem). We use this gap repeatedly in \S\ref{sec:analysis}.

\subsection{Corpus}
\textbf{257 hand-authored canonical facts} --- people, places, employers, multi-hop chains, and facts that
change over time --- are buried under \textbf{400 distractor messages} so that a fixed top-$k$ retriever cannot
win by returning everything. Total \textbf{657 messages}; a top-10 retriever sees \sapp1\% of the corpus per
query. Every gold answer is grounded in exactly one canonical fact, so a miss is always a retrieval/answer
failure, never a missing fact.

\section{Question taxonomy}\label{sec:taxonomy}

460 questions across \textbf{eight capability classes}. Each class isolates a distinct memory operation; the
parenthetical is the question count. Because the two friends are modelled as \emph{people Max knows}, their own
attributes are \textbf{relational} (one hop from Max) and their networks are \textbf{multi-hop}.

\cat{flat-recall}{34 questions}
\textbf{Tests:} retrieval of a single atomic fact about the user, stated once and never changed.
\textbf{Why:} the simplest memory operation and the floor for any system --- if you cannot return a fact you
were told verbatim, nothing else matters. \textbf{Scoring:} LLM judge (semantic match to the gold answer).
\textbf{Examples:}
\begin{itemize}[nosep]
  \item \emph{``What is Max's profession?''} $\to$ robotics engineer
  \item \emph{``What instrument does Max play?''} $\to$ violin
  \item \emph{``What is the name of Max's cat?''} $\to$ Biryani
\end{itemize}

\cat{relational}{90 questions}
\textbf{Tests:} a fact reached by \emph{one hop} from the user --- an attribute of a person, place, or thing
Max is directly connected to. \textbf{Why:} real assistant queries are rarely about the user in isolation
(``what does my sister do,'' ``where do my parents live''); one-hop traversal is the common case. The class is
large (90) because it is where terse, structured stores tend to lose the \emph{relation} that disambiguates an
answer. \textbf{Scoring:} LLM judge. \textbf{Examples:}
\begin{itemize}[nosep]
  \item \emph{``What is the name of Max's sister?''} $\to$ Anita
  \item \emph{``Where do Max's parents live?''} $\to$ Portland
  \item \emph{``What does Max's friend Priya do for work?''} $\to$ perception engineer
\end{itemize}

\cat{multi-hop}{118 questions}
\textbf{Tests:} a fact reached by \emph{two or more hops} (Max $\to$ A $\to$ B $\to$ attribute). The largest
class, and the one structure is supposed to own. \textbf{Why:} answering ``what does my best friend's wife do''
requires chaining relationships, not matching a sentence; it separates systems that \emph{model} connections
from those that merely store text. \textbf{Scoring:} LLM judge. \textbf{Examples:}
\begin{itemize}[nosep]
  \item \emph{``What does Max's brother-in-law do for work?''} $\to$ cardiologist
  \item \emph{``Where does Max's best friend work?''} $\to$ Stripe
  \item \emph{``What does Priya's husband do?''} (Max $\to$ Priya $\to$ husband $\to$ occupation)
\end{itemize}

\cat{temporal-update}{90 questions}
\textbf{Tests:} facts that \emph{changed} over the corpus --- the system must return the \emph{current} value
and not the superseded one (and sometimes recall the prior value on request). \textbf{Why:} memory that never
updates is worse than useless; a system that answers ``Portland'' after the user moved to Denver is actively
wrong. Probes supersession and recency handling. \textbf{Scoring:} LLM judge (current value required; stale
value marked wrong). \textbf{Examples:}
\begin{itemize}[nosep]
  \item \emph{``What city does Max currently live in?''} $\to$ Denver (he previously lived in Portland)
  \item \emph{``What company does Max currently work for?''} $\to$ Cobalt Robotics
  \item \emph{``What city did Max live in before his current one?''} $\to$ Portland
\end{itemize}

\cat{enumeration}{34 questions}
\textbf{Tests:} returning a \emph{complete typed set} (``list all X''), not just one member. \textbf{Why:}
completeness is a different skill from point lookup --- a store can reliably return \emph{a} family member yet
never assemble \emph{all} of them. This is the structural store's natural strength (typed edges enumerate
cleanly) and the keyword store's natural weakness. \textbf{Scoring:} \textbf{deterministic set recall} ---
the fraction of gold members surfaced, no LLM judge, nothing to spin. \textbf{Examples:}
\begin{itemize}[nosep]
  \item \emph{``List all of Max's family members.''} $\to$ \{Anita, Deepak, Sunita, Raj, Mira, Felix, \ldots\}
  \item \emph{``Name every company Max has worked for.''} $\to$ \{Cobalt Robotics, Northwind Logistics\}
  \item \emph{``List the musical instruments played by people in Max's life.''} $\to$ \{violin, viola, harp\}
\end{itemize}

\cat{aggregation}{23 questions}
\textbf{Tests:} a count or filter computed \emph{over} the stored facts (``how many\ldots''). \textbf{Why:}
requires not just retrieval but correct counting of the retrieved set --- and punishes stores that surface a
polluted block, since a stray entity inflates the count. \textbf{Scoring:} LLM judge against the gold count.
\textbf{Examples:}
\begin{itemize}[nosep]
  \item \emph{``How many companies has Max worked for?''} $\to$ two (Cobalt Robotics, Northwind Logistics)
  \item \emph{``How many cities has Max lived in?''} $\to$ two (Portland, Denver)
  \item \emph{``How many children does Max's sister Anita have?''} $\to$ two (Mira, Felix)
\end{itemize}

\cat{absence}{48 questions}
\textbf{Tests:} correctly answering \textbf{``no''} to a plausible-but-false premise --- each baited with a
tempting distractor about \emph{someone else}. \textbf{Why:} a memory system that hallucinates a confident
``yes'' to something it was never told is dangerous; this class measures resistance to that failure. The bait
ensures a system cannot pass by keyword-matching a near-miss. \textbf{Scoring:} existence-aware judge; a
confident ``yes'' to a non-existent thing is a hallucination (wrong). \textbf{Examples:}
\begin{itemize}[nosep]
  \item \emph{``Does Max have a brother?''} $\to$ No (one sibling, his sister Anita; his \emph{brother-in-law}
  Raj is the bait)
  \item \emph{``Does Max play the piano?''} $\to$ No (he plays violin; his grandmother was the pianist --- bait)
  \item \emph{``Does Max own a dog?''} $\to$ No (his only pet is a cat, Biryani)
\end{itemize}

\cat{presence-control}{23 questions}
\textbf{Tests:} genuine ``yes'' questions, structurally identical to the absence class. \textbf{Why:} a
\emph{control} --- without it, a system could game the absence suite by answering ``no'' to everything. Strong
absence \emph{and} strong presence-control together demonstrate genuine discrimination. \textbf{Scoring:}
existence-aware judge. \textbf{Examples:}
\begin{itemize}[nosep]
  \item \emph{``Does Max have a sister?''} $\to$ Yes (Anita)
  \item \emph{``Does Max own a cat?''} $\to$ Yes (Biryani)
  \item \emph{``Does Max play a musical instrument?''} $\to$ Yes (the violin)
\end{itemize}

\section{Systems under test}\label{sec:systems}

Seven systems span four retrieval philosophies. Understanding the architecture predicts the per-category
profile (\S\ref{sec:analysis}).

\begin{description}[style=nextline,leftmargin=1em,nosep]
  \item[Naive RAG (vector)] Chunk-level vector store: raw messages embedded with \texttt{nomic}, top-$k$
  cosine retrieval. No structure --- the control for ``just retrieve the text.''
  \item[Mem0 (consolidating vector)] Vector store with \emph{LLM-driven consolidation}: at write time it merges
  and rewrites related statements into dense, deduplicated memory records.
  \item[CI-Server (graph)] Extracts typed entities and relationships into a property graph; recall is an entity
  search plus a one-hop expansion over \emph{serialized nodes} (name + description). Structure-first.
  \item[CI-Server (hybrid)] The graph above \emph{unioned} with a raw-message vector channel
  (\S\ref{sec:hybrid}) --- structure for traversal, raw text for fidelity.
  \item[OpenViking (context DB)] Volcengine context database; VLM-based extraction into a structured context
  store.
  \item[TencentDB Agent Memory] SQLite + \texttt{sqlite-vec}; per-message extraction with vector recall.
  \item[Holographic (keyword + HRR)] SQLite FTS5 keyword search plus Holographic Reduced Representations ---
  \emph{no} LLM and \emph{no} embeddings. The minimal-cost baseline.
  \item[Hindsight (retain/recall)] A retain/recall service with \texttt{bge-small} embeddings; serialized
  recall (its client errors under concurrency).
\end{description}

\section{Per-category performance analysis}\label{sec:analysis}

The headline ranks systems; the per-category profile explains them. Each architecture has a signature.

\paragraph{\texttt{flat-recall} --- raw text wins, distillation loses.}
The atomic fact (``violin'') is present verbatim in one source sentence, so any store that keeps the sentence
returns it (Naive/OpenViking/TencentDB 26; hybrid \best{32}). Mem0 is \emph{lowest} of the serious systems
(23): its consolidation rewrites statements and occasionally drops an atomic detail in favour of a summary.
The graph (25) usually has the fact on the node but sometimes only as a terse field that the answerer reads
past.

\paragraph{\texttt{relational} --- the graph's weak spot, the raw sentence's strength.}
Naive leads (\best{86}) because ``Max's sister Anita'' lives in a single chunk that contains both the
\emph{relation} and the \emph{answer}. The vanilla graph is the field's worst (60): distilling ``Anita'' into a
\texttt{sister} edge and a terse node strips the surrounding context, so the answerer retrieves the right
entity but cannot tell which relation it satisfies, or answers a competing entity (``Max has two managers'').
This single weakness --- storage (366.7) far exceeding answer (349.0) --- is the clearest precision failure in
the study, and the one the hybrid most directly fixes (60 $\to$ 85).

\paragraph{\texttt{multi-hop} --- structure and consolidation beat flat retrieval.}
Here the ordering inverts: Mem0 leads (\best{109}) because its dense records \emph{bundle} a chain of related
facts into one retrievable unit; OpenViking (106) and the graph configurations (96/102) traverse explicitly;
Naive is the worst of the capable systems (80) because flat chunks cannot chain --- a two-hop answer requires
two different chunks to co-occur. This is the category that justifies structure at all.

\paragraph{\texttt{temporal-update} --- the hybrid's largest margin.}
The hybrid (\best{86}) dominates because both modalities help: the graph carries supersession (current vs.\
prior edges) and the raw channel carries the explicit sentences (``moved to Denver,'' ``before that,
Portland''). Single-modality stores trail (Mem0 78, graph 66, Naive 64): consolidation can overwrite the prior
value, flat retrieval can surface the stale chunk with equal rank to the fresh one.

\paragraph{\texttt{enumeration} --- structure assembles sets; keyword collapses.}
The typed graph enumerates cleanly (graph 27, hybrid \best{30}): a ``list all family'' query walks the typed
edges and returns the complete set. Flat and consolidating stores miss members (Naive 23.4, Mem0 24.9 ---
whichever chunks fall outside top-$k$ are simply absent). Holographic \emph{collapses} (13.6): keyword
matching cannot assemble a typed set it was never asked for by name. This is deterministic set recall --- the
one unspinnable column, and the graph's signature strength, retained by the hybrid.

\paragraph{\texttt{aggregation} --- uniformly hard; counting prose is brittle.}
No system clears 18/23. The task asks the answerer to \emph{count} a retrieved set, and an LLM tallying prose
miscounts whenever the context is polluted --- the graph is worst (14) because a one-hop expansion can pull a
neighbour's relative into the block (``5 employers,'' counting a friend's sister). The robust fix is to count
\emph{typed edges on the graph} rather than ask an LLM to tally text --- correct by construction, though this
benchmark's $N=23$ cannot resolve the delta.

\paragraph{\texttt{absence} / \texttt{presence-control} --- discrimination, not retrieval.}
These move together and cluster tightly (most systems 40--46 / 19--22) because they test the \emph{answerer's}
willingness to say no, given context, more than retrieval depth. The hybrid edges absence (\best{46}): richer
context lets the answerer confirm a thing is genuinely absent rather than guess. Presence-control sits near
ceiling for everyone --- a useful confirmation that no system games the absence suite by reflexively answering
``no.''

\paragraph{Summary of signatures.} \emph{Vector/raw-text} systems own single-hop, flat, and temporal (the
source sentence preserves context); \emph{structural} systems own enumeration and help multi-hop (typed edges
assemble and chain); \emph{consolidation} (Mem0) is the strongest single modality on multi-hop; \emph{keyword}
(Holographic) is cheap but collapses where typed structure is required. No single modality is best everywhere
--- which is exactly why the union wins.

\section{The hybrid retrieval channel}\label{sec:hybrid}

The per-category analysis points to one conclusion: the graph and the raw text are \emph{complementary}, and
the gap between CI-Server's vanilla graph (76\%) and the leaders was the text it discarded. An extraction graph
embeds only the distilled \emph{nodes} (name + description) and drops the source sentence; the detail that
disambiguates a relational or temporal answer lives in that sentence.

\textbf{Mechanism.} The hybrid adds a second retrieval channel: a vector search over the \emph{raw messages},
unioned with the graph traversal. Every recall returns graph nodes \emph{plus} one-hop expansion \emph{plus}
the nearest source sentences. Structure provides enumeration and multi-hop reach; the raw text provides
single-hop and temporal fidelity. The merge is the \emph{plain union with no cap or re-ranking}: on a
soft-spot-weighted sweep the uncapped union beat reciprocal-rank fusion and relevance re-ranking by \sapp6\,pp,
because capping drops answer-bearing lines and the reasoning answerer already tolerates the larger context.

\textbf{Result.} Implemented natively (CI-Server embedding and searching its own messages through the existing
\texttt{nomic} pipeline, no second store): \textbf{91.1\%}, field-best. The per-category recovery is exactly
what the analysis predicts --- relational 60$\to$85, temporal 66$\to$86, flat 25$\to$32 (the raw-text
categories) --- \emph{while retaining} enumeration (27$\to$30) and multi-hop (96$\to$102) (the structural
categories). The hybrid is not a better graph; it is the graph plus the modality the graph was missing.

\section{Conclusions}

\begin{itemize}[nosep]
  \item \textbf{The per-category profile is the result; the headline is a summary of it.} Each architecture has
  a signature --- raw text for single-hop/flat/temporal, structure for enumeration/multi-hop, consolidation for
  multi-hop --- and these are mechanistic, not incidental.
  \item \textbf{No single modality is best everywhere, so the union wins.} CI-Server (hybrid) leads at 91.1\%
  by combining graph traversal with raw-text vector retrieval, recovering the graph's single-hop precision
  while keeping its complete-set strength. The transferable lesson: \emph{an extraction pipeline should not
  discard its source text} --- re-introducing it was worth $+$15\,pp.
  \item \textbf{Mem0 is the strongest single-modality system} (86.9\%, best multi-hop) but identity-fragile on
  multi-entity corpora; raw retrieval is robust.
  \item \textbf{Interpret per-category numbers against the noise floor} ($\pm$8 to $\pm$16\,pp); and remember
  these systems are single-user by design, so a multi-user benchmark measures artifacts, not capability.
\end{itemize}

\section{Methodological notes and threats to validity}\label{sec:validity}

\begin{description}[style=nextline,leftmargin=1em,nosep]
  \item[Distance metric.] \texttt{nomic} embeddings are unnormalised ($\|v\|\approx 22$), so vector recall must
  use cosine (\texttt{<=>}) not L2 (\texttt{<->}); an L2 threshold silently returns nothing. All vector paths
  (Naive, the hybrid channel, the graph's semantic mode) use cosine.
  \item[Judge robustness.] \texttt{ornstein} is a reasoning model that spends tokens before emitting the
  schema-constrained verdict; it is given a generous token budget and retries transient failures, with a loud
  \texttt{JUDGE\_UNSCORED} flag rather than a silent wrong. All reported numbers use the hardened judge (0 judge
  failures).
  \item[Resolution limit.] Per-category effect sizes below the noise floor ($\pm$8 to $\pm$16\,pp) are not
  measurable at this $N$. Small read-side recall tweaks to CI-Server fell below it; only the hybrid channel ---
  a large, additive lever --- cleared it. A focused single-class micro-suite (200+ questions) is the instrument
  for finer effects.
  \item[Extraction non-determinism.] \texttt{gemma} extraction varies run-to-run, so any change requiring a
  re-ingest carries an extraction-variance confound; same-store read-side comparisons (e.g.\ disabling the
  graph expansion: $-30$) are the clean ones.
  \item[Single-user validation.] The abandoned multi-persona design is retained only as evidence for the
  single-user design choice (\S\ref{sec:single-user}): consolidation stores bound a second persona's
  first-person facts to a prominent other entity; the graph mis-anchored them to its canonical self node.
\end{description}
