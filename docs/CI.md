# Running CI for this repo

Automatic workflow triggers in this repository are **gated**: pushing does not
start a GitHub-hosted run any more. Checks run on local hardware, and the
workflows that remain are started deliberately.

Why: GitHub Actions was costing the org $563/month, almost all of it hosted
compute for checks that run just as well on hardware we already own.

Starting a gated workflow needs the [`gh` CLI](https://cli.github.com) and push
access. `--ref` matters - the workflow file is read from that branch, so a
workflow that only exists on your feature branch must be dispatched against it.

Full cross-repo runbook: `CI-Local-CICD/RUNBOOK.md` (regenerate with
`ci-local docs`). This file is generated - do not hand-edit.

> ### ⚠️ `publish.yml` is dispatched on a release TAG, never on `main`
>
> `publish.yml` resolves the image version from the ref: its
> `Resolve VERSION from tag` steps run
> `tag="${GITHUB_REF#refs/tags/}"; version="${tag#v}"`, so a branch ref leaves
> `VERSION=refs/heads/main` — slashes and all, not a legal image tag. A
> `Refuse to publish a non-release ref` guard runs first in **all three** of its
> jobs (`verify-ci-passed`, `build`, `merge-and-register`), before any checkout,
> testing `GITHUB_REF` against the workflow-level `RELEASE_TAG_RE`. That makes
> the mistake cheap rather than correct: the run still ends red and no release
> is produced.
>
> The **Cut a release** block below now emits `--ref <release-tag>` and the
> tagging command, so it is safe to copy. It used to say `--ref main`; that was
> fixed at the source in CI-Local-CICD#11 rather than patched here, for the
> reason given above. The same default remains correct in the **Run a check
> workflow on GitHub** section — none of those workflows read a version out of
> the ref.
>
> What the generated block cannot tell you is which gates must be green first.
> `verify-ci-passed` loops over a `GATED_WORKFLOWS` list in `publish.yml`, and a
> REQUIRED entry with no green run **at that commit** fails the job. Two are
> required today (`ci.yml`, `migration-integrity-check.yml`); `e2e.yml` is
> advisory, so a missing e2e run only warns — which means a green gate does not
> prove the app works end to end. Re-derive the list rather than trusting this
> paragraph; it is one env block:
> `sed -n '/GATED_WORKFLOWS:/,/^        run:/p' .github/workflows/publish.yml`.
>
> ```bash
> git tag v2026.7.27 origin/main && git push origin v2026.7.27
> # Every REQUIRED gate, dispatched on the tag ref and green before the next line.
> gh workflow run ci.yml --repo companionintelligence/CI-Server --ref v2026.7.27
> gh workflow run migration-integrity-check.yml --repo companionintelligence/CI-Server --ref v2026.7.27
> # Advisory today, but dispatch it too — it is the only full-stack proof there is.
> gh workflow run e2e.yml --repo companionintelligence/CI-Server --ref v2026.7.27
> gh workflow run publish.yml --repo companionintelligence/CI-Server --ref v2026.7.27
> ```
>
> `git tag <tag> origin/main` names the commit rather than checking it out, so
> it works from a git worktree — `git checkout main` fails outright when the
> default branch is checked out elsewhere.
>
> The emergency escape is `skip_test_gate=true`, which REFUSES a blank
> `bypass_reason` and writes the reason into the run's step summary. It is not
> theoretical: `v2026.9.9` and `v2026.9.9.1` both shipped that way while
> `ci.yml` was red. `v2026.9.10` was the first release since 2026-08-19 to pass
> the gate on its own merits.

### Native suites are not in `make test`

`make test` covers the JS and Python stacks only. The two native suites need
toolchains a backend-only machine has no reason to carry, so they are their own
targets — each checks its prerequisites first and names the fix when one is
missing:

| Target | Runs | Needs |
|---|---|---|
| `make test-android` | `./gradlew testDebugUnitTest` in `frontend/apps/android/android` — 100 JVM tests across `:app`, `:ci-capacitor-local-hub`, `:ci-capacitor-local-llm`, `:ci-capacitor-speech` | JDK 21, an Android SDK with `platforms;android-36` located via `ANDROID_HOME` / `ANDROID_SDK_ROOT` / `local.properties`, and `yarn install` having been run inside `frontend/apps/android` |
| `make test-desktop` | `cargo test` in `frontend/apps/desktop/src-tauri` — **42 `#[test]` declarations as counted 2026-09-07, but no single host compiles all 42.** Six are platform-gated: 4 macOS-only (`local_model/apple_bridge.rs`, whose whole module is `#[cfg(target_os = "macos")]` at `local_model/mod.rs:26`) and 2 Linux-only (the rootless-Docker tests in `stack_manager.rs`, each carrying its own `#[cfg(target_os = "linux")]`). So the count you should see is **36 cross-platform + gates: 38 on Linux, 40 on macOS, 36 on Windows.** A host-to-host disagreement is expected and those are the numbers it should land on — anything else is a lost test, not a `cfg`. This total moved twice in one afternoon — **recount, do not quote.** | A Rust toolchain, plus (Linux) the GTK/WebKit `-dev` packages `desktop-build.yml` installs |

The **instrumented** Android suites (`src/androidTest`) are in neither the make
targets nor CI: they need a booted device. Run them by hand against an emulator
with `./gradlew connectedDebugAndroidTest`.

Both counts above were re-derived 2026-09-07 and will drift the moment someone
adds a test — the Rust one moved twice while this page was being written, so
treat every figure here as a timestamped observation and recount. Neither recipe
needs a JDK, an Android SDK or a Rust toolchain — they are `grep`:

```bash
# Android JVM tests (100): :app plus the three plugin modules, whose sources
# live under frontend/packages/, not under the android app.
find frontend/apps/android/android/app/src/test frontend/packages/capacitor-*/android/src/test \
  -type f \( -name '*.kt' -o -name '*.java' \) -exec grep -c '@Test' {} + \
  | awk -F: '{s+=$2} END {print s}'

# Rust tests: prints the DECLARATION total across all platforms (42 on
# 2026-09-07), which is not what any one host runs — subtract the gates below.
# Two details are load-bearing: scan `src` only, never `target/` (vendored
# build scripts carry their own #[test]s), and anchor on the start of the line
# — stack_manager.rs's comments say "#[test]" in prose three times, which an
# unanchored grep counts as three tests that do not exist.
grep -rEc '^[[:space:]]*#\[(tokio::)?test\]' frontend/apps/desktop/src-tauri/src --include='*.rs' \
  | awk -F: '{s+=$2} END {print s}'

# The gates, so the per-host arithmetic above can be re-derived rather than
# trusted. This finds a target_os cfg sitting directly above a #[test] — it
# does NOT find a whole module gated at its `mod` declaration, which is how
# apple_bridge.rs's four are excluded, so check `local_model/mod.rs` too.
grep -rn -B1 '^[[:space:]]*#\[(tokio::)?test\]' -E frontend/apps/desktop/src-tauri/src \
  --include='*.rs' | grep 'target_os'
```

### Cut a release

Dispatch these on a **release tag**, never on `main`: the workflow resolves its version from the ref it ran on, so a branch ref produces a version like `refs/heads/main` rather than a number. Tag the commit first, then dispatch on the tag:

```bash
git tag v2026.1.1 origin/main && git push origin v2026.1.1
```

(Naming the commit rather than checking it out keeps this working from a git worktree, where the default branch may already be checked out elsewhere.)

**Publish** — `publish.yml`

```bash
gh workflow run publish.yml --repo companionintelligence/CI-Server --ref <release-tag> -f skip_test_gate=false -f bypass_reason=<string>
```
