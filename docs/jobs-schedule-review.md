## Q1. Is the schedule complete and correct?

**Verdict: correct in structure, wrong in a dozen specifics, and materially incomplete on retention.** The wrapper, the durable `ci.cron_runs` table, the role gate and the advisory-lock discipline are all well-designed. What is broken is (a) a set of one-line defects that make the dashboard lie, (b) three schedules that scan unbounded tables at high frequency, and (c) three data classes that grow forever because nobody scheduled their reclamation.

### 41 vs 43 — reconciled

Exactly two crons carry `role: 'worker'` and never register in the web process: `ImportStageListener.ts:104` (the import crash-recovery sweep, `'30 */5 * * * *'`) and `StagedUploadPurgeCron.ts:51` (`'0 17 * * * *'`). `Cron.ts:76` returns the raw descriptor without calling `NestCron` when `!serves(role)`, and `JobMonitorService.getCronSchedules` (line 316) enumerates only *this process's* registry. 43 − 2 = 41.

**Caveat:** this only holds on a role-split deployment. `config.role` defaults to `'all'` (`configuration.ts:59`) and `serves()` returns true for both roles under `'all'` (`common/roles.ts:21-25`), so a bare `yarn dev` or a single-container appliance registers and shows all 43. If you are seeing 41, the box is running `CI_ROLE=web` with a separate worker — and the two invisible schedules are both *recovery* work, which is precisely the category you want visible. Fix: `ci.cron_runs` already holds rows from every process, so union the registry with the persisted names and render worker-only rows with `nextRunAt: null`.

### Schedules that are registered but do nothing

Twelve rows on the card are permanent no-ops in the default/production config profile:

- **11 under `smart.rotation`** (`config/default.json:211` = `false`): the ten `SmartRotation*Cron` classes (`SmartRotationScheduledCrons.ts:13,24,35,46,57,71,82,93,104,115`), each returning at `SmartRotationService.ts:47-49`, plus `EntityPromotionCron.ts:28-30`.
- **1 under `agent.memory.compaction`** (`default.json:207` = `false`): `MemoryCompactionCron.cronCompactMemories` fires every 5 minutes and returns at lines 41-45.

Two things to know. First, this is a config decision, not dead code — `config/development.json:20` sets `smart.rotation: true` and `custom-environment-variables.json:216` maps `ENABLE_SMART_ROTATION`, documented (commented out) at `.env.default:149`. Second, the design is deliberate mutual exclusion, not duplication: `FeedQueueCron.ts:24`, `AnswerInferenceCron.ts:23` and `PythonFunctionCrons.ts:67-71` all stand down when the flag is **on**. So the appliance runs either the legacy set or the rotation set, never both.

The real exposure is the six work types with no legacy equivalent — `graph_link`, `graph_enrich`, `context_prompt`, `schedule_sync`, `hydrate_answers`, `hydrate_things`. `SmartRotationListener` is the only recurring caller of `GraphEnrichmentService`, `CrossTableHydrationService` and `SuggestionSyncService`, so on a production appliance those never run at all.

The dashboard cannot tell you any of this. `getCronSchedules` (`JobMonitorService.ts:305-348`) reports registration and last-fire only. Worse, `CronRunStore.record()` is stamped *before* the body (`Cron.ts:57-58`), so `ci.cron_runs` shows a fresh "last run" for a tick that returned on a feature gate.

### What is missing entirely

- **Import staging reclamation.** `ci_import.staged_items` / `staged_entities` / `staged_relationships` all `REFERENCES ci_import.import_runs(id) ON DELETE CASCADE` (`migrations/20260810164304_create_ci_import_schema.sql:114,180,272,340`), and the schema header (lines 17-24) calls staging "a scratchpad for one run, not a second copy of the user's data." Nothing deletes a run outside tests — no cron, no `@Delete` route (`ImportRunsController` is `@Get`/`@Post` only, lines 168-457), no non-test `DELETE FROM ci_import.*`. `StagedUploadPurgeCron` only touches `staged_sources` rows and upload *bytes* under a 24 h TTL. Completion-time cleanup is filesystem-only (`ImportStageListener.ts:300` → `rm -r`). So every parsed record's staging row — metadata JSONB, original location, content hash — survives forever beside the `ci.*` row it produced. The only path that removes them is deleting the user's account. **Size it before choosing a TTL** (`SELECT pg_total_relation_size('ci_import.staged_items')`); the on-disk cost was not measured here.
- **`ci_etl.connection_sync_jobs` retention.** The only `DELETE` is per-id (`ConnectionSyncJobService.ts:213`), reachable solely from a GraphQL mutation (`ConnectionSyncJobResolver.ts:111`). Growth is gated by sync completion, not by the cron cadence — but it is monotonic.
- **Dead-letter reclamation.** `migrations/20260809032723_create_pipeline_control_plane.sql:208` states rows "never expire — the payload is often the only surviving copy of the record." Defensible for *unreplayed* letters. But already-replayed ones are equally permanent (replay only stamps `replayed_at`, `PipelineRunService.ts:977-983`) even though the partial index `pipeline_dead_letters_unreplayed_idx ... WHERE replayed_at IS NULL` (line 219) already excludes them from the replay path. The writer is scheduled and batched — 500 rows every 2 minutes (`pipeline/constants.ts:614,621`), a 360k/day ceiling — with no cap of any kind on the destination.
- **Overdue detection.** `ci.cron_runs` is written by exactly one place (`CronRunStore.ts:33`) and read by exactly one (`:48` → `JobMonitorService.ts:310`), to fill a dashboard cell. Nothing compares `last_run_at` to a cadence; a repo-wide grep for "overdue" returns only unrelated planning code. `JobsPage.tsx:389` renders `cron.running ? 'scheduled' : 'stopped'` off `isActive`, which stays true for a schedule whose body throws every tick (`Cron.ts:63-72` catches, logs, returns). And because the stamp precedes the body, "Last run: 2 minutes ago" is true of a cron that has succeeded at nothing for weeks. A cron that stopped enqueuing also produces no dead letters, so it is invisible there too. **Fix: compute `overdue` server-side, and stamp a second column after the body returns so "last attempted" and "last succeeded" are distinguishable.**
- **Missed-window catch-up.** Eight single-shot fan-outs have none: `dailySummaries` `'0 10 0 * * *'`, `weeklySummaries` `'0 15 0 * * 1'`, `monthlySummaries` `'0 20 0 1 * *'`, `hbpeNightly` `'0 30 2 * * *'` (`PythonFunctionCrons.ts:102,107,112,149`), `JobMetricsCollector.purgeOnSchedule` `'0 25 4 * * *'`, `hydrate_answers` / `hydrate_things` `'0 5 3 * * *'` / `'0 15 3 * * *'` (`types.ts:44-45`). `AccountPurgeCron.ts:9-17` states the operating assumption these violate: "An appliance is often off; an hourly tick means a box that is up for one hour a day still honours the promise." The singleton key already makes them safe to re-invoke — `fn:<name>:<user>:<dayKey>` (`PythonFunctionCrons.ts:180-182,250`) dedupes within a day — so an hourly re-call of `fanOut` closes the gap at the cost of one deduplicated dispatch per user per hour. A box asleep at 00:10 currently produces no daily summary and no record that it didn't.
- **Embed/vector coverage monitoring.** See Q4.
- **A schedule for `OrphanCleanupService.cleanOrphans()`** (`search-ingress/services/OrphanCleanupService.ts:97`). The sweep exists, is bounded and batched, and is driven by `ENTITY_SOURCE_MAP` — its only callers are two manual routes (`MaintenanceController.ts:1112,1131`).
- **TimescaleDB policy health.** 12 `add_compression_policy` calls and exactly one `add_retention_policy` (`hbpe.prediction_log`, 90 days, in three duplicate migrations). `screen_captures` is a hypertable with no compression policy at all; `api_logs` has no retention. Nothing reads `timescaledb_information.job_stats`, so a policy job that never launches or repeatedly fails is silent. Also: the image is stock `postgres:18.4-bookworm` with Timescale layered on (`infrastructure/database/Dockerfile:11,28`), so `timescaledb-tune` never ran, and a repo-wide grep for `max_worker_processes` / `max_background_workers` returns nothing. **Not demonstrated as broken — verify on the appliance with `SELECT job_id, proc_name, hypertable_name, last_run_status, total_failures, last_successful_finish FROM timescaledb_information.job_stats;` before treating it as a defect.**

### Smaller correctness items

- **No cron declares a `timeZone`.** `Cron.ts:80` forwards options straight to `NestCron`, so `cron@4.3.0` falls back to `Intl.DateTimeFormat().resolvedOptions().timeZone` (`dist/time.js:29-32`). The shipped image sets no `TZ` and mounts no `/etc/localtime`, so it resolves UTC — which is the only reason `PythonFunctionCrons.ts:31`'s "Cron layout (UTC…)" docblock is accurate rather than enforced. Setting `TZ`, or running `make dev` in a developer's local zone, silently re-times all 43 schedules. `EnrichmentWindowService.resolveTimeZone` (`:846-847`) reads the same value, so the two cannot currently disagree. The resolved zone is already in the DTO (`JobMonitorService.ts:341`) and typed in `useJobsDashboard.ts:51,85` — just never rendered.
- **Twelve schedules fire on second 0 of every hour.** Four crons were deliberately second-offset (`'10 */2'`, `'20 */5'`, `'30 */5'`, `'40 */2'`); the rest were not. At minute 0 the set includes both `JobMetricsCollector` full-table scans, all four unbounded `SyncOrchestrator` scans, and `MemoryCompactionCron`'s 100-fragment LLM batch, all sharing one 25-connection TypeORM pool (`application.ts:96`) and one event loop. Individually cheap; collectively an amplifier for everything above. One-line fix per cron.
- **A duplicate cron name would be silently discarded.** `SchedulerRegistry.addCronJob` does throw on a duplicate, but it is never reached: the orchestrator de-duplicates first with a plain object assignment (`dist/scheduler.orchestrator.js:89-95`). All 43 names are currently distinct, but they are hand-written literals — a copy-paste repeat in `SmartRotationScheduledCrons.ts` (ten near-identical classes in one file) would delete a schedule at boot with no log line and no exception. The wrapper already sees every `runName` at decoration time; a module-level set plus a post-bootstrap count check catches both this and defect #1.
- **`PlanningJobsCron`'s five expressions are the only hand-written 5-field ones** (`:18,20,22,24,26`). They parse correctly — `cron@4.3.0` right-aligns fields and defaults seconds to `'0'` (`dist/time.js:244-249`, `dist/constants.js:12-13`) — but `'15 * * * *'` beside 6-field neighbours reads as "every 15 seconds." Normalise for the next reader. (Note: `CronExpression.EVERY_MINUTE` and `EVERY_HOUR` are also 5-field, so this is a consistency nit, not a uniqueness claim.)

## Q2. Too many, not enough, or the wrong type?

**Verdict: roughly the right number of jobs, but the mix is skewed — too much polling, not enough measurement, and no retention layer at all.**

Break the 43 down by what they are actually for:

| Kind | Count (approx) | Assessment |
|---|---|---|
| Poll-for-work loops (`SyncOrchestrator` ×3, `AnswerInferenceCron`, `FeedQueueCron`, `PlanningJobsCron` ×5, pipeline ticks ×2) | ~12 | **Too many, too fast.** Most are "sweep everything and see if anything is due" on a 30–60 s timer. Nearly all have a due-time or claim column available (`providerEndpoint` TTL, `ci.pipeline_state`, `transform_claimed_at`) that would let them select only due rows. |
| Derivation / enrichment fan-outs (`PythonFunctionCrons` ×9, `SmartRotation*` ×10, `DailyMetricsCron`, `InitialActionsCron`, `MemoryCompactionCron`, `EntityPromotionCron`) | ~23 | **About right in count, but 12 are inert** and one is a duplicate driver with a dead name. Net live derivation work is roughly half what the card suggests. |
| Rollup / metrics (`ActivityRollupCron`, `JobMetricsCollector` ×2) | 3 | **Right idea, wrong shape** — both do unbounded recomputes. |
| Reclamation (`AccountPurgeCron`, `StagedUploadPurgeCron`, `JobMetricsCollector.purge`, `DeadLetterReaper`) | 4 | **Not enough.** Three growing data classes have no purge at all (import staging, sync-job history, replayed dead letters), and the dead-letter reaper *creates* permanent rows rather than bounding them. |
| Health / measurement | **0** | **The real gap.** Nothing measures embed coverage, retrieval recall, index orphans, Timescale policy health, or whether a cron is overdue. Every one of these is computable today from code that already exists. |

**The wrong type, specifically:** this is a schedule built for *doing* and not for *knowing*. Every derived output has a producer; almost none has a check that the producer worked. `EmbedCoverageTelemetryService.ts:55-61` records the consequence in its own docblock — coverage holes (content 0/366,862; event 2,743/42,376 = 6.5%) "went unnoticed until measured by hand." The service that would have caught them exists and has exactly one caller: an HTTP route (`MaintenanceController.ts:1220`) whose comment assumes a metrics scraper outside the repo will poll it. There is no scraper.

**What to *remove*, not add:** `EntityPromotionCron`, the second pipeline tick, and the per-minute cadence on `AnswerInferenceCron` and `SyncOrchestrator`. That is four fewer schedules and a substantial cut in steady-state load before adding anything.

**One structural note that also affects load:** `PipelineSliceListener.ts:61-71` registers all three pipeline queues (index, enrich, embed) with **no** `role`, which defaults to `'web'` (`PGBossEventService.ts:270`). So the 6-wide embed drain runs inside the API process, sharing its event loop and its global-10 semaphore with request handling — it is not in the worker. Giving those queues `role: 'worker'` is a small change with a real effect on interactive latency during a backfill.

## Q3. What hardware do you need?

**Verdict on the GPU question, plainly: a GPU is strongly recommended, not required — and the reason is architectural, not throughput.** The LLM path is deliberately serial. `LLM_QUEUE_OPTIONS` sets `localConcurrency: 1` (`domains/llm/constants.ts:20`), and the comment at lines 4-7 says the 1 exists so jobs "cannot stampede a 1–2 slot local GPU." Two other queues do the same: image description (`:40`) and thing vision (`:56`). Because there is exactly one LLM slot, there is no parallelism to hide CPU latency behind — a slow generation is felt directly as an interactive chat turn waiting. `INTERACTIVE_JOB_PRIORITY = 10` (`domains/events/constants.ts:42`) reorders the queue but Ollama does not preempt, so a chat turn still waits out whatever is in flight.

What keeps that slot busy: `AnswerInferenceCron` emits exactly one grounded RAG turn per user per minute (`QuestionService.ts:933` — `WHERE rn <= 1`), and the seeded question catalogue is 492 + 217 rows plus a 1,274-row reflections catalog. The queue does *not* grow unboundedly — `policy: 'short'` plus `singletonKey: infer:${userId}:${questionId}` (`AnswerInferenceCron.ts:49`) caps it at one pending inference per user — but the slot is occupied essentially continuously until that backlog is answered.

**Everything else is CPU, RAM and disk.** The embedding path in particular should not motivate a GPU purchase: it is worker-bound, not model-bound.

### Sizing tiers

| | **Minimum** (it works) | **Recommended** (a real corpus) | **Comfortable** (headroom) |
|---|---|---|---|
| CPU cores | 4 | 8 | 16 |
| RAM | 16 GB | 32 GB | 64–128 GB |
| GPU | none | 12–16 GB VRAM | 16–24 GB VRAM |
| DB volume | 512 GB NVMe | 1 TB NVMe | 2 TB NVMe |
| Scratch volume | shared (risky) | 256 GB, **separate, not tmpfs** | 512 GB, separate |
| `shared_buffers` | 2–4 GB | 8 GB | 16 GB |
| What breaks | HNSW index build; embed backfill runs for days; chat waits behind answer inference | nothing routine; a 350 GB unpack still needs the scratch tier raised | — |

**Derivations behind those numbers**

- **Cores.** Import parse is single-slot appliance-wide by design — `IMPORT_STAGE_CONCURRENCY = { unpack: 1, parse: 1, media: 2, push: 1 }` (`import/constants.ts:91-96`), because "six abreast … starved the event loop and the connection pool until Skip on an onboarding page hung" (`ImportStageListener.ts:124-128`). Reserve ~5 cores of headroom during an import (1 parse + 2 media + unpack + push), and remember the pipeline queues run in the *web* process, so an import and a backfill contend there.
- **Concurrency ceilings cap what extra cores buy.** The shipped values are `queues.concurrency: 10`, `perQueueConcurrency: 6`, `embedding.concurrency: 4`, `embedding.batchSize: 32` (`config/default.json:141-150`). Three independent places agree 10/6 is intended (`docs/runbooks/pipeline-operations.md:784`, `BackpressureService.ts:24-25` and `:439-440`). **Note a config bug:** `configuration.ts:315-317` and `:280` declare zod defaults of 32/20/12 that can never fire, because `z.default()` only applies to an *absent* key and node-config has already supplied one. Any plan that assumes more than 10 global in-flight jobs must set `CI_QUEUE_CONCURRENCY` / `CI_EMBED_CONCURRENCY` (`custom-environment-variables.json:100,115`).
- **Embedding throughput.** `DEFAULT_SLICE_SIZE = 200` (`pipeline/constants.ts:420`), sized for "~60 s of work for a mid-cost stage" (`:413-414`), run 6 abreast (`BackpressureService.ts:86-97`). 6 × 200 / 60 s = **1,200 rows/min → ~11.5 h** for the 826,478-item corpus the repo stages against (`video/stage.real-corpus.sh:13`). **This is a slice-budget model, not a measurement** — the repo performs the same arithmetic at `BackpressureService.ts:120-122`, but if an embed slice actually runs faster than 60 s the ceiling moves and the bound shifts to the 4 × 32-text HTTP path. Timing one slice would replace both estimates with a fact. Either way: buy cores and raise the caps, not VRAM.
- **RAM — the 16 GB wall is the HNSW build.** `BULK_LOAD_RUNBOOK.md:178-181` states plainly that "HNSW build memory on ~400k × 768-dim rows is not yet quantified on appliance hardware," and the index is created by a plain blocking `CREATE INDEX` with no `WITH` clause (`migrations/20260701120100_add_embeddings_hnsw_index.sql:27-29`), so pgvector defaults apply. A pgvector-derived (not repo-derived) estimate at 826k rows is ~2.8 GB of `maintenance_work_mem` for the build, on top of `shared_buffers`. On 16 GB there is no room for it: either the slow on-disk build path or the OOM killer takes Postgres. Build it out-of-band with `CREATE INDEX CONCURRENTLY` on an existing corpus. It is already on the deferral list (`deferrableIndexes.ts`, formerly `IndexDeferralService.ts:54-58`, "The single most expensive index to maintain during a large load").
- **VRAM.** Two Ollama models are required (`REQUIRED_OLLAMA_MODELS` in `scripts/xtask/commands/dev.ts`, which `make dev` pulls: `nomic-embed-text`, `gemma4:e4b`) and HBPE loads its own llama.cpp GGUF *in-container* with `n_gpu_layers=-1` (`hbpe/qwen.py:50-51`) — `Qwen3.5-0.8B-Q8_0`, "~800 MB" per `qwen.py:13`. **`gemma4:e4b`'s byte size is stated nowhere in the repo**; ~5–6 GB is class-derived from the E4B naming and `configuration.ts:23-27`'s explicit contrast with `gemma4:31b`, not a repo fact. Working total ≈ 7–8 GB → 12 GB practical floor. No dedicated vision model is needed: `resolveServedChatModel` picks a served model reporting the `vision` capability (`OllamaService.ts:772-800`) and non-multimodal models are caught and skipped (`ImageDescriptionListener.ts:135-146`); the 27B pin only applies when `pinned.demo.models` is on (`default.json:191` = `false`).
- **Disk — two volumes, two different floors, and no reliable multiplier.** Scratch: `PREFLIGHT_MARGIN_BYTES = 1 GiB` above the declared archive size (`unpack.ts:265,671`); an unpacked Takeout runs 40–50 GB and "`/tmp` is tmpfs on a stock appliance, so extracting there consumes RAM until the machine dies" (`configuration.ts:322-326`); the repo's worst case is a 350 GB unpack, referenced in eight files. Database: a hard `DATABASE_FREE_FLOOR_BYTES = 2 GiB` check that refuses to start (`storage/databaseSpace.ts:36`, `UnpackStage.ts:57-71`), added because "a 2.7 GB Takeout filled a 96 GB VM and the push died mid-run" and surfaced as an OCI error rather than a disk-full message (`databaseSpace.ts:14-17`). **Do not turn that anecdote into a ratio** — `UnpackStage.ts:59-62` says explicitly that "how many database bytes an archive becomes is not predictable from its size, so this is a floor check, not an estimate." In a split-container topology set `CI_IMPORT_DB_DATA_DIR` (`custom-environment-variables.json:137`) or the free-space probe can't see the volume and you get the OCI error instead of a diagnosis.
- **Images.** HBPE CPU image ≈ 5 GB (derived from `backend/apps/hbpe/Dockerfile:39`: the `chown` it replaces "cost 1.7 GB — about a third of the published image"). The CUDA (`nvidia/cuda:12.9.2-cudnn-devel-ubuntu22.04` + torch 2.13) and ROCm (`rocm/dev-ubuntu-22.04:7.2.4-complete`) variants are several times that; **no size is recorded in the repo — measure with `docker image ls` rather than guessing.**
- **Postgres connections are fine and add up with headroom.** `max_connections=200` (`infrastructure/database/Dockerfile:77`), 197 non-reserved. Deterministic consumers: api 25 (TypeORM, `application.ts:96`) + 10 (pg-boss, `PGBossEventService.ts:140`) = 35; worker another 35 (same module graph via `createApplicationContext`, `main.ts:23`); HBPE 20 (`hbpe/database.py:25`). Total 90/197. The one uncapped consumer is summary-service — `poolclass=NullPool` (`summary/database.py:29`), bounded in practice only by `function_runner_concurrency: 2` (`summary/config.py:139`). Give it a bounded `QueuePool`.
- **Two Node heaps, not one,** if you run the split topology (`Procfile:1-2`).

## Q4. What other jobs would make this smarter?

Ranked by value ÷ effort. **Two "obvious" ideas are already built — do not rebuild them:**

- **Anomaly detection over a daily feature store already exists and runs hourly.** `DailyMetricsCron` (`'0 10 * * * *'`) → `DerivationScanService.scanAll()` (`DailyMetricsCron.ts:79`) → `CorrelationEngine.scan` → `AnomalyEngine.scan` → `SuggestionEngine.propose`, writing `ci_derived.metric_correlations` / `metric_anomalies` / `metric_suggestions` / `suggestion_arms` (`migrations/20260817210000_create_ci_derived_findings.sql:8,35,55,77`), with detectors `robust_z`, `cusum`, `hbpe_l0`.
- **The HBPE forecast scoring loop is closed.** `nightly_runner.py:339` calls `drift_detection()` → `scoring.score_and_store` (`scoring.py:549`), reached as `step5_drift` (`functions.py:130`). The older "collected but never computed" audit finding no longer applies.

### Tier 1 — build these (high value, low effort, no user data mutated)

1. **`RetrievalHealthCron` — daily coverage snapshot.** Call the existing `EmbedCoverageTelemetryService.computeCoverage()` (`:87`, threshold 0.9 at `:170`) on a schedule, persist the result, and raise a `ci.actions` row when a type hits zero or drops week-over-week. **Critical detail:** `computeCoverage` counts `ci_search.embeddings` only, while `ci_search.vectors` is the actual search *candidate* source (`ObjectMergeService.ts:513`) — so run the same counts against both, or a type can read "healthy" while being invisible to search. 18 types (`search-next/types.ts:1-26`) × 4 index-served counts = 72 counts per run. **This is the single highest-value addition**: the derivation layer's failure mode is silence, and this is the one job that converts silence into a signal.
2. **Import staging reclamation cron.** Beside `StagedUploadPurgeCron`, `role: 'worker'`: delete `ci_import.import_runs` rows in a terminal state older than N days; the `ON DELETE CASCADE` makes that complete. If run history must survive, split the TTL — keep `import_runs` / `import_stages` for 90 days, drop the `staged_*` payload days after a successful push. Measure first.
3. **Dead-letter purge leg** on the existing reaper: `DELETE ... WHERE replayed_at IS NOT NULL AND replayed_at < now() - interval '30 days'`. Then decide separately whether unreplayed letters get a long TTL or a per-(queue, stage) cap.
4. **Schedule the orphan sweep that already exists** — `OrphanCleanupService.cleanOrphans()` nightly, dry-run count logged, bounded batches. It shares `ENTITY_SOURCE_MAP` with the coverage service, so #1 and #4 can be one nightly sweep.
5. **`DerivationCron` — the seven orchestrator legs nobody calls.** `ORCHESTRATE_STAGES` declares 16 legs (`MaintenanceOrchestratorService.ts:51-68`); nine are covered (`COALESCE_STAGES` at bulk-push finish, plus `SmartRotationListener.ts:163`'s three). Seven have no caller but HTTP/CLI: `heal_self_collation`, `materialize_edges`, `normalize_relationships`, `derive_relationships`, `fold_notes`, `extract_graph`, `media_dimensions`. **`derive_relationships` is the prize** (`MaintenanceOrchestratorService.ts:362` → `DerivedRelationshipService.derive`, `:26`): idempotent SQL upserting L2 edges — `COMMUNICATES_WITH` from person-person pairs with `strength = LEAST(1.0, LN(n+1)/LN(10)/2.0)` (`:58-90`), `FREQUENTS` from `VISITED`, all `ON CONFLICT DO NOTHING` with same-transaction `graph_deltas`. No LLM, no egress, set-based. Suggested `'0 40 4 * * *'`, staggered off HBPE (02:30) and the bootstrap sweep (03:00), fanned out per user with the `PythonFunctionCrons.fanOut` singleton-key shape. **Drop `materialize_edges` from the proposal** unless you first confirm the `promote.edge_*` pipeline stages don't already cover it — its own docblock says "Operator-invoked … Never auto-run" (`DeterministicEdgeBackfillService.ts:92-93`).
   ⚠️ **Mutation flag:** the two aggregate legs only project edges the user's data already asserts and can run unconditionally. The **household-`Group` reification mints a new entity** and must go behind `decideAction({ kind: 'graph_entity' })` — `GRAPH_CONNECTION_KINDS` includes it (`PersonalizationService.ts:19-24`), and `decide()` returns `'review'` in balanced (`:173`) and `'review'`/`'skip'` in cautious (`:161`); only `hands_off` auto-applies, at ≥ 0.7 (`:123`).

### Tier 2 — build these next (high value, medium effort)

6. **Object/Item duplicate detection.** `DuplicateDetectStage` covers `Person` only (`CANDIDATE_ENTITY_TYPE = 'Person'`, `:28`; source predicate `:133-142`). A scored object detector already exists and is thrown away on every call: `ObjectDuplicateService.findDuplicateGroups` (`:137`) with reasons identifier / product_name / brand_model, `MIN_IDENTIFIER_LENGTH = 6`, `MAX_GROUP_SIZE = 6`, and `ci.entity_merge_blocks` filtering (`:243`) — its only caller is a GraphQL read (`ItemResolver.ts:533`) that recomputes from scratch and writes nothing. The executor exists (`ObjectMergeService.mergeObjects`, `:164`) and the target table needs no migration (`migrations/20260809184710_clean_stage_support.sql:81` — `entity_type` is bare `TEXT` with no CHECK). Port it into a ledgered nightly stage writing `ci.merge_candidates` under `entity_type = 'Object'`. Follow the sibling's two-generation pattern (`:44`, `:62`) and its hard rule: the source predicate must never mention `ci.merge_candidates` (`:125-132`). **Safe by construction** — that table is proposal-only ("CLEAN proposes; it never merges", `migration :96`). **Do not extend to `Place`:** there is no `PlaceMergeService`, so a Place proposal would have no executor.
7. **`RecallProbeCron` — measure and then choose `ef_search`.** `SearchService.semanticSearch` (`:309`) puts `user_id` and the type filter *outside* the HNSW ordering (`:329-341`), so a type-filtered query can return far fewer than its `LIMIT 25` while the exact answer exists. A repo-wide grep for `ef_search` returns exactly one hit and it is prose (`migrations/20260803223022_create_object_observations.sql:128`); `hnsw.iterative_scan` returns zero. **Both pgvector recall knobs are at their defaults and recall has never been measured.** Weekly, inside the enrichment window: sample ~50 rows per type, run the production query against an exact query (`SET LOCAL enable_indexscan/enable_bitmapscan = off`), record recall@25, then re-run at `ef_search` 100/200/400. Cost: 50 × 18 types = 900 embeddings of already-stored text ≈ 29 batched Ollama calls; the exact leg is the expensive half (a seq scan over ~1.1 GB of 768-dim vectors), so cap it. Measurement only.
8. **Prefer `value_e164` in duplicate scoring — not a new cron, a small edit.** `IDENTIFIER_KIND_SCORES` discounts phone to 0.85 (`DuplicateDetectStage.ts:170`) with a comment (`:161-167`) saying the discount is provisional "until `clean.identifier_normalize` gives every claim an E.164 form." That condition is now met: `toE164` exists (`IdentifierNormalizeStage.ts:205`), `writeIdentifiers` sets `value_e164` (`:700`), the column exists on `ci.identifier_claims` (`migration 20260809183010:116`) and `ci.entity_identifiers` (`migration 20260809184710:59,64-66`), and both claim producers write it (`PersonSelfClaimStage.ts:190,257-264`; `PersonLinkStage.ts:1082+`). A grep for `value_e164` inside `DuplicateDetectStage.ts` returns zero. Score exact E.164 above 0.85, last-10-only below; bump `DUPLICATE_SCORING_GENERATION` 1→2 (`:44`) and `STAGE_VERSIONS['clean.duplicate_detect']` in the same commit. Respect the stated contract (`:34-43`): a rescore never resurrects a human-rejected pair.

### Tier 3 — build with care (mutation risk)

9. **`EntityTypeAuditCron`.** Entity retyping is currently done by hand-written one-off migrations — six landed in 48 hours (18–19 Aug 2026: `20260818220731`, `20260819002002`, `20260819055246`, `20260819092314`, `20260819145023`, `20260819150902`). The classification rule is already shared code (`isShortCode`, `import/staging/identity.ts:84`, called from `datasources/imessage.ts:637` and `datasources/googlevoice.ts:70`); nothing re-applies it to rows already in `ci.entities`. A weekly windowed audit that re-runs the classifiers and **files disagreements as reviewable proposals** would turn a recurring migration into a standing job.
   ⚠️ **Two hard constraints, both verified.** (a) A type change *moves the natural key* — `imessage.ts:628` states the fix "must move `linked_id` as well as `entity_type`" — so retyping without re-keying mints permanent duplicates on the next import. (b) A retype *out of* `Person` orphans the search index, because the person embed sweep's predicate is `entity_type = 'Person' AND merged_into_entity_id IS NULL` (`pipeline/stages/index/entityEmbedStages.ts:172`, mirrored at `entityRows.ts:157`) — stale `ci_search` rows must be deleted in the same transaction. **Must sit behind `decideAction({ kind: 'graph_entity' })`; never auto-UPDATE.**

### Tier 4 — speculative or blocked

10. **`ChangeDigestCron` (speculative, low value as scoped).** A per-entity "what changed about X this week" rollup over `ci.graph_deltas`. Lower value than it first appears: `LifeContextService.ts:53` already selects the 20 most recent deltas into the insights leg (`SmartRotationListener.ts:117`) — though only when `smart.rotation` is on. The genuine gap is narrow: no per-subject, per-period aggregation. Cost would be one grouped scan per user plus an optional short LLM call for ~10 surfaced entities/user/week. 11. **Salience / temporal-decay scoring — BLOCKED, do not build.** `ci.event_analytics` has `salience DOUBLE PRECISION DEFAULT 1.0` and `access_count INTEGER DEFAULT 0` (`migrations/20260808150100_schema_consolidation.sql:48-51`), backfilled once and then referenced in exactly two non-functional places (a comment at `EventEntity.ts:129`, an assertion in `EventService.ranking.test.ts:73`). The access signal is equally absent, and worse than it was: `ci.entities.last_accessed` was `DEFAULT NOW()` (`migration 20250925144000:44`) with nothing ever UPDATE-ing it, and the same 2026-08-26 pass dropped it entirely from both `ci.events` and `ci.entities` (`20260826202418`), since after 14 months neither column had a writer or a reader. Not a new cron. Divergence between the two stores is not provable from code alone.
