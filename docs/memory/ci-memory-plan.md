## 1. The Core Distinction: Two Layers, One Database

Most "agent memory" products are purpose-built stores that exist solely to serve AI agents. CI is different: it is a **full personal data operating system** that *also* exposes an agent memory API. These are not the same thing, and conflating them obscures CI's real strategic position.

### Layer 0 — Companion Memory Database (Personal Digital Twin)

This is what CI fundamentally **is**: a user-owned, local-first, permissioned personal data store. It is not a feature; it is the product. Everything that makes CI valuable — data sovereignty, rich entity graph, multi-source ETL, provenance, privacy controls — lives here.

Layer 0 contains:

- **Identity & access** — users, actors (user-actor, agent-actor, device-actor), API keys with scope sets, consent preferences
- **Knowledge graph** — Person, Place, Event, Concept, Content, Communication, Item entities; typed edges (KNOWS, LIVES_IN, ATTENDED, PREFERS, …); Apache AGE graph extension
- **Files & documents** — uploaded files, DocumentParserService (text extraction → chunking → embedding), chunk→fact pipeline
- **Communications** — threads, messages, conversation history
- **Browser activity** — history captured by the browser extension
- **ETL-ingested data** — Google Contacts, Facebook Friends/Profile, with provenance recording per transform; more sources in roadmap
- **Semantic search index** — pgvector cosine similarity + tsvector keyword hybrid, both against entity embeddings and document chunks
- **Measurements & position** — TimescaleDB hypertables for sensor data, GPS, AR headpose
- **LLM summaries** — hourly/daily/weekly narrative summaries generated by `summary-service`
- **Behavioral predictions** — HBPE (Hierarchical Behavior Prediction Engine) model output
- **Provenance & audit** — lineage trail on every entity/relationship, full audit log
- **Privacy & consent** — per-category consent preferences, right-to-erasure endpoint
- **Data export** — full JSON portability export endpoint

### Layer 1 — Agent Memory Provider (Adapter on Top of Layer 0)

This is an **application** of the personal database, not a separate store. It exposes Layer 0 to AI agents (Hermes, OpenClaw, Claude Code, custom agents) through a narrow API contract. The agent memory layer is powered by the real personal data; it does not maintain a shadow copy.

Layer 1 contains:

- `POST /v1/memory/context` — receives agent conversation turns, persists to `agent_context_log`, returns a context injection string
- **AgentContextService** — semantic search over the entity index (pgvector, 0.65 cosine threshold) → K-hop=1 graph expansion → formatted injection string (1,200-token budget)
- **`hermes-companion-memory` plugin** — Python, implements Hermes `MemoryProvider` ABC; `prefetch` + `sync_turn` + lifecycle hooks
- **`openclaw-companion-memory` plugin** — TypeScript, implements OpenClaw memory slot
- **`ermy-memory-setup.sh`** — post-install provisioning script; creates a scoped `agent_memory:write` API key
- **`eval/personal_context_v1.jsonl`** — 50 evaluation prompts for measuring recall quality

## 2. LifeScope: The Predecessor

CI's Layer 0 is the spiritual and architectural successor to **LifeScope Labs** ("The Internet of You"), an open-source personal data platform that Companion Intelligence's founders built and eventually sunset.

LifeScope's thesis was correct: every person generates a rich, queryable digital life across dozens of platforms, and they should own it. Its implementation collected API data from Facebook, Twitter, Google, Pinterest, Spotify, GitHub, Instagram, and others; stored it in MongoDB with a GraphQL interface; and offered Feed, Map, Timeline, VR, and AR views.

What LifeScope lacked — and what made it difficult to sustain — was the AI-native layer that makes personal data *actively useful* rather than just *stored*. CI makes the following upgrades:

| LifeScope | CI adds |
|---|---|
| MongoDB + GraphQL (cloud) | Postgres + pgvector + Apache AGE (local-first) |
| Manual query / UI browsing | LLM summarization (hourly/daily/weekly) |
| Static data views | HBPE behavioral prediction engine |
| No agent surface | MCP tool surface + agent memory API |
| No embedding/semantic search | pgvector hybrid semantic + keyword search |
| No privacy controls beyond auth | Per-category consent, right-to-erasure, portability export |
| Cloud-hosted | Self-hosted on CI-Hub; user owns the hardware |
| No provenance tracking | Full provenance lineage on every entity and relationship |

### 2.1 LifeScope's Data Model (Technical)

LifeScope organized personal data around six core object types:

| Object | Description |
|---|---|
| **Events** | The primary atom. Every user action (sent message, listened to song, visited webpage, made purchase) becomes an Event with `datetime`, `type`, and `context` fields. |
| **Content** | Digital objects attached to events: images, videos, files, web pages, emails — each with `mimetype`, `text`, `title`, `url`. |
| **Contacts** | Per-handle objects: each social-media handle or email address is a separate Contact. A **People** layer let users manually group handles into a single real person. |
| **Locations** | Four subtypes: (1) provider-recorded, (2) app-tracked, (3) uploaded GeoJSON, (4) **estimated** — a background worker backfilling location onto events with no native geotag by nearest timestamp. |
| **Connections** | OAuth credentials for a specific provider (one row per provider per user). |
| **Saved Searches** | Persistent, named search queries as first-class objects. |

**tagMasks** were a three-way tagging model: `source` (platform-assigned), `added` (user-added), `removed` (user-stripped). The intersection defined live tags on any object.

### 2.2 LifeScope's Technical Architecture

| Component | Technology |
|---|---|
| **Backend API** | Node.js + `graphql-compose-mongoose` auto-generating GraphQL from Mongoose schemas |
| **Database** | **MongoDB** — relationships modeled as UUID arrays resolved via GraphQL hydration at query time, not as traversable graph edges |
| **Frontend** | Vue.js / Nuxt.js SPA — Feed, List, Map, Gallery, Timeline, VR (A-Frame/WebXR), AR views |
| **ETL** | Separate Node service; per-provider scripts; upsert-by-hash deduplication |
| **Hosting** | Cloud-hosted on AWS (not local-first) |

Companion services: **LifeScope-XR** (VR/AR memory palace), **LifeScope-Voice** (conversational interface), **LifeScope-Browser-Extension** (passive capture).

### 2.3 The Ten LifeScope Limitations CI Addresses

| # | Limitation | CI response |
|---|---|---|
| 1 | No intelligence layer — retrieval-only, never reasoned over data | LLM summarization pipeline + HBPE predictions |
| 2 | Manual identity resolution — Contact→People grouping was manual, no ML dedup | Multi-actor model; ML dedup planned |
| 3 | MongoDB not a graph DB — relationships were arrays, not traversable edges | Postgres + Apache AGE (Cypher graph traversal) |
| 4 | No AI/LLM integration anywhere | Ollama local LLM; multi-provider routing planned |
| 5 | No agent/MCP surface — data was for the user's eyes only | MCP server (stdio + HTTP), GraphQL subscriptions, SSE |
| 6 | No vector search / semantic embeddings | pgvector HNSW (1536-dim nomic-embed-text) + hybrid retrieval |
| 7 | No predictive layer | HBPE (PyTorch + ONNX + Qwen3, nightly train + INT8 inference) |
| 8 | No privacy/consent API | agent_access_policies + consent receipts + PII redaction at egress |
| 9 | No provenance tracking | entity_provenance + ingest_runs + DERIVED_FROM edges |
| 10 | Cloud-hosted on AWS, not local-first | Docker Compose stack on CI-Hub; user owns hardware |

For the full technical comparison including schema evolution details, see [companion-memory-architecture.md](companion-memory-architecture.md).

## 3. Competitive Landscape

### 3.1 Personal Memory Database / Digital Twin

The field trying to build Layer 0 is sparse relative to its importance.

| Product | Approach | Gap vs. CI |
|---|---|---|
| **Solid/Pods** (Tim Berners-Lee) | Decentralized personal data pods, RDF data model | No AI, no embeddings, no agent API, adoption has stalled |
| **Apple Intelligence** | On-device semantic index, Spring 2026, Apple-only | Walled garden, no multi-source ETL, no open API, no portability |
| **Google Takeout / My Activity** | Export-only archives | Not a live queryable DB; no AI; no agent surface |
| **Olares / Olares One** | Local-AI appliance, Kubernetes-based personal cloud, $2.34M Kickstarter | No memory-specific intelligence, no knowledge graph, no agent memory API |
| **Rewind / Limitless** | Screen + audio recording, acquired by Meta Dec 2025 | Now controlled by Meta; no graph; no portability; privacy concerns |
| **MyData (open standard)** | Consent-based data portability spec | Specification only, no implementation |
| **LifeScope** (predecessor) | Open-source personal data platform | Sunset; no AI layer; cloud-hosted |

**CI's position in Layer 0:** No current product combines local-first deployment, a live knowledge graph with vector search, LLM summarization, multi-source ETL, and an open agent API. This is the moat.

### 3.2 Agent Memory Provider

The agent memory market is moving fast. Every competitor here is building a *purpose-built store just for agents*; none of them are exposing a real personal database.

| Product | Funding | Approach | Key limitation vs. CI |
|---|---|---|---|
| **Mem0** | $24M raised, ~$150M valuation | Two-phase LLM extraction + vector store; 41K GitHub stars, AWS SDK exclusive | Cloud-first; no personal DB behind it; shadow copy of agent conversations only |
| **Honcho / Plastic Labs** | $5.35M | Dialectic modeling + Neuromancer-XR 8B user model | Cloud LLM dependency; no local data; no personal database |
| **Letta / MemGPT** | $10M | OS-style tiered memory; agent self-edits memory blocks | Agent-centric; no real personal data; cloud-first |
| **Zep / Graphiti** | — | Bi-temporal knowledge graph; SOTA on DMR benchmark (94.8%) | Purpose-built for agent conversations; no multi-source ETL or personal data |
| **Supermemory** | $3M | "Plaid for memory"; simpler vector store | No graph; no personal data; no local-first option |
| **Cognee** | $7.5M | Graph-based memory; >1M pipelines/month | No personal database; no local-first |

**CI's position in Layer 1:** CI's agent memory layer is backed by the user's *actual* personal data (contacts, documents, calendar history, browser activity). Competitors are storing summaries of agent conversations. When a Hermes agent asks "what does this person know about Alice?", CI can answer from real contact records, past conversations, and relationship edges — not just from what the agent happened to say about Alice in previous sessions.

## 4. CI's Moat: "Personal Data OS"

The strategic framing for investors and partners is not "we have better agent memory." That market is crowded, under-moated, and prone to consolidation by foundation model providers (who can add memory natively).

The correct frame is: **CI is the personal data OS**. Agent memory is table stakes — an expected affordance of owning personal data — not the differentiator.

The defensible moat comes from:

1. **Data flywheel** — every connected source, every uploaded document, every browser capture enriches the entity graph; the graph becomes more valuable the longer the user has it
2. **Local-first sovereignty** — the data never leaves the user's hardware without explicit consent; this is a structural advantage over any cloud-first competitor as privacy regulation tightens
3. **Provenance and explainability** — every entity knows where it came from; users can audit, correct, and delete at the granularity of individual records
4. **Cross-app utility** — the same database powers the web SPA, XR clients, wearables, and any agent; it is not locked to a single application or agent framework
5. **LifeScope lineage** — years of thinking about what a personal data platform needs; the graph model, ETL patterns, and view surfaces are proven concepts being rebuilt AI-natively

## 5. Implementation Roadmap

The roadmap below treats Layer 0 as **already implemented** (the knowledge graph, ETL, embeddings, search, privacy, provenance, export are all in place). The milestones focus on Layer 1 maturity.

### 5.1 MVP v1 — Logging (Implemented)

- `POST /v1/memory/context` endpoint accepts agent turn data
- `AgentContextLogEntity` — persists sessions, turn index, raw messages to `ci.agent_context_log`
- Hermes plugin (`hermes-companion-memory`) — `sync_turn` posts turns in daemon thread; `prefetch` returns empty string
- OpenClaw plugin (`openclaw-companion-memory`) — equivalent TypeScript implementation
- `ermy-memory-setup.sh` — provisions `agent_memory:write` scoped API key on install
- Returns `{injection: "", memoryId, entitiesUsed: []}` — stable contract for v2

### 5.2 MVP v2 — Retrieval (Implemented)

- `AgentContextService.retrieveInjection` — derives query from last user message
- `SearchService` semantic search (pgvector, cosine threshold 0.65, max 8 seed entities)
- K-hop=1 graph expansion via `GraphQueryService.getRelationships`
- Injection string formatted with 1,200-token budget; seed entities first, neighbours second
- Hermes plugin `prefetch` hook wires up injection to system prompt prepend
- Failures are non-fatal; service returns empty injection on any retrieval error

### 5.3 MVP v3 — Intelligence (Next)

| Item | Detail |
|---|---|
| Turn-to-entity ingest | Extract facts from agent turns and write them back to the knowledge graph as semantic entities; set `memory_id` on `AgentContextLogEntity` |
| v2 tool surface | Expose Hermes tool schemas for direct graph queries: `search_memory`, `get_entity`, `list_relationships` |
| Configurable thresholds | Surface cosine threshold and injection token budget as per-user settings via the agent-memory settings API |
| Multi-agent sessions | Support concurrent agent sessions with per-session context isolation |
| Eval harness integration | Run `eval/personal_context_v1.jsonl` against v3 and publish recall / precision metrics |

### 5.4 Later

| Item | Detail |
|---|---|
| Memory-kind aware retrieval | Use the episodic/semantic/procedural kinds from plan 03 to weight retrieval by query intent |
| Predictive injection | HBPE prediction output prepended to injection when predicted relevance is high |
| Cross-agent sharing | Controlled sharing of entity subgraphs between agents via scoped API keys |
| OpenAI / Anthropic SDK adapters | Thin wrappers so any app using those SDKs gets CI injection without a dedicated plugin |
| Federation | User-to-user entity sharing via CI-Portal broker |

## 6. Hermes Plugin Specification

The `hermes-companion-memory` plugin implements the Hermes `MemoryProvider` ABC.

### 6.1 Lifecycle hooks

| Hook | When called | Behavior |
|---|---|---|
| `is_available()` | On Hermes startup | Returns `True` if `COMPANION_API_KEY` is set |
| `initialize()` | Once per agent session | Creates `CompanionClient`, generates `session_id` UUID |
| `prefetch(query)` | Before each LLM call | v1: `""`; v2: calls `GET /v1/memory/injection?q=…` (not yet wired) |
| `sync_turn(user, assistant)` | After each completed turn | Posts to `POST /v1/memory/context` in daemon thread; never blocks |
| `on_session_end()` | Session teardown | Posts `__session_end__` sentinel |
| `on_pre_compress()` | Before context window compression | Posts `__pre_compress__` sentinel |

### 6.2 Configuration

| Variable | Required | Default |
|---|---|---|
| `COMPANION_API_KEY` | Yes | — |
| `COMPANION_BASE_URL` | No | `https://api.companion.intelligence` |
| `COMPANION_AGENT_ID` | No | `null` |

### 6.3 Hardware tiers

CI runs entirely on the user's hardware. The Hermes plugin is designed to work across:

| Tier | Hardware | Notes |
|---|---|---|
| Minimal | 8 GB RAM, no GPU | Ollama with quantized (Q4) embedding model; pgvector CPU-only |
| Standard | 16 GB RAM, discrete GPU | Ollama nomic-embed-text or mxbai-embed-large; pgvector HNSW with GPU |
| Performance | 32+ GB RAM, CUDA/ROCm/Metal | Full embedding + HBPE inference on-device; summary service at full speed |

## 7. Evaluation Metrics

The agent memory layer is measured against three dimensions:

| Metric | Target | Measurement |
|---|---|---|
| Context retrieval precision | ≥ 0.80 P@K | `eval/personal_context_v1.jsonl` — 50 prompts, judge by ground-truth entity presence in injection |
| Injection latency (p99) | < 200ms | Measured at `POST /v1/memory/context` under concurrent load |
| False positive rate | < 0.10 | Fraction of injection lines with no relevance to the query |
| Turn persistence rate | 100% | Every `sync_turn` call results in a persisted `agent_context_log` row |
| Agent loop availability | 100% | Retrieval failures must never crash or block the agent |
