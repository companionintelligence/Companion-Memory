## 4. §6.4 (duplicate `FileService`) — root cause reclassified, still broken

The old baseline's theory — two classes both named `FileService` (`domains/files/services/FileService.ts` vs `domains/memory/services/FileService.ts`) colliding in `ActivityModule`'s DI graph — **does not survive live diagnosis**.

Live check via `yarn run exec -- <diagnostic script>` (mirrors `make seed`'s ts-node+@swc/register pipeline):

```
FilesFileService === MemoryFileService: false
FilesFileService has aggregateHourlyActivity: function
MemoryFileService has aggregateHourlyActivity: undefined
=== design:paramtypes on ActivityRollupService ===
6 FileService | === FilesFileService: true | === MemoryFileService: false
```

`ActivityRollupService`'s constructor correctly resolves the `@ci/domains/files` `FileService` token — **not** memory's. No string-token registration exists (`grep -rn "provide:\s*['\"]FileService" src/` — zero hits), and `files/index.ts` / `memory/index.ts` each export their own `FileService` from separate, never-merged barrels — ordinary per-module provider scoping, not a collision.

**Actual mechanism**, traced end-to-end:

1. `backend/apps/api/scripts/seed-database/main.ts:8` imports the correct `@ci/domains/files` `FileService`.
2. `main.ts:61-63`: `createAdminTestingModule().overrideProvider(FileService).useValue({})` stubs object-storage methods away for seeding (per `scripts/support/admin-testing-module.ts:24-39`).
3. By NestJS's exact-token semantics, this override replaces the files-domain `FileService` provider **everywhere it's injected in the compiled graph** — including in `ActivityRollupService` (`src/domains/activity/services/ActivityRollupService.ts:8,76,90`), which needs the *same token* for an unrelated capability (`aggregateHourlyActivity()`).
4. `ActivityRollupCron.onApplicationBootstrap()` (`src/domains/activity/cron/ActivityRollupCron.ts:30-38`) fires `refreshRollup()` fire-and-forget as soon as `module.init()` runs, gated only by `serves('web')` (`src/common/roles.ts:20-23`), which defaults `true` — always fires for `make seed`.
5. `refreshRollup()` → `refreshAll()` → for the `'files'` source, `fileService.aggregateHourlyActivity()` is called on the `{}` stub → `TypeError: fileService.aggregateHourlyActivity is not a function`, caught and swallowed per-source in `refreshAll()`'s own try/catch (`ActivityRollupService.ts:106-124`) — matching the confirmed symptom exactly, non-fatal but silently broken.

The existing coverage test (`scripts/support/__tests__/admin-testing-module.test.ts`) does not catch this by design — its own docstring states `.compile()` "resolves and constructs providers but runs no lifecycle hook," so `onApplicationBootstrap()` never runs there.

**Diagnosis:** not a DI/module-resolution collision — an **over-narrow test double**. `main.ts` stubs `FileService` to `useValue({})` to avoid touching object storage during seeding, but the override is token-scoped, not call-site-scoped, so it also blanks a completely different method (`aggregateHourlyActivity`) that a different consumer (`ActivityRollupService`) needs from the same token.

**Fix** (renaming either class fixes nothing — there's no real collision to resolve): widen the stub in `scripts/seed-database/main.ts:61-63`:

```ts
.overrideProvider(FileService)
.useValue({ aggregateHourlyActivity: async () => [] })
```

Optionally also strengthen `admin-testing-module.test.ts` to call `.init()` with lifecycle hooks (not just `.compile()`), so a future stub/bootstrap-hook mismatch like this fails that test instead of only surfacing via `make seed` against a live stack.
