## 6. Confirmed defects

### 6.1 P0 — `useAuth` consumes `getLaunchUrl` on Android, contradicting its own comment and test

`frontend/apps/web/src/hooks/useAuth.ts:643` guards the cold-start deep-link consumption with `isNativePlatform()`, which is true on **both** iOS and Android. Six lines above, the comment reads:

> iOS often cold-starts from Safari's "Open with Companion", so we also consume `getLaunchUrl` **there** — web and Android keep the live listener only.

This was a **deliberate** change: `c109353d7 fix(mobile): route Android through device-connect like iOS` replaced `isIosPlatform()` with `isNativePlatform()` and dropped the import, to "resume cold-start `companion://` deep links on Android as well as iOS". It updated neither the comment nor `useAuth.test.tsx:744`, which still asserts Android must **not** call `getLaunchUrl`.

Two committed decisions now contradict each other and the suite is reporting it honestly. **This needs a human decision, not a test edit.** The reason the assertion exists matters: `DeviceConnectPage/oidc.ts:250` *also* calls `getLaunchUrl()`, and a Memory-login one-time code can only be redeemed once (`claimNativeOidcCode`, whose comment reads "Claim a Memory-login one-time code so iOS `getLaunchUrl` cannot redeem it"). Whether two consumers on Android race for that code is the actual question. `isIosPlatform()` is still exported from `@ci/common` if the answer is to revert.

### 6.2 P0 — the iOS lane of `mobile-build.yml` cannot pass

Two independent, reproducible defects. Either alone fails the build.

**(a) The Safari-extension fallback can never succeed.** `frontend/apps/ios/scripts/sync-safari-extension.sh` fills the extension from a sibling `CI-Browser-Extension` checkout, else downloads a pinned release. Both paths are broken for CI:

- `EXT_DIR` is derived as `<repo-root>/../CI-Browser-Extension`. In a **git worktree** that resolves to `.claude/worktrees/CI-Browser-Extension`, which does not exist. In GitHub Actions there is no sibling checkout at all.
- The fallback then requests `v${PINNED_VERSION}` with `PINNED_VERSION=1.5.0`. **The only release/tag in `companionintelligence/CI-Browser-Extension` is `v1.4.0`** → `release not found` → `Command PhaseScriptExecution failed`.
- Even pointed at `v1.4.0`, the script looks for a `*safari-mobile.zip` asset. That release ships `chrome.zip`, `firefox.zip`, `sources.zip` — **no safari-mobile asset exists in any release.**

So the iOS build only works for someone who happens to have a sibling clone at exactly the right path.

> **2026-08-29 follow-up — is this fixable from CI-Server alone? No.** Investigated whether
> `mobile-build.yml`'s iOS job could clone `CI-Browser-Extension` directly (its default branch, `master`,
> at a pinned ref) into the sibling path before the Xcode build, sidestepping the need for a published
> release entirely. It cannot, for two independent reasons, verified live via `gh api`:
>
> 1. **`companionintelligence/CI-Browser-Extension` is a *private* repo** (`gh api
>    repos/companionintelligence/CI-Browser-Extension --jq '.visibility'` → `private`). A `git clone`/
>    `actions/checkout` of it inside CI-Server's Actions job needs a credential with read access to that
>    repo. `gh secret list --repo companionintelligence/CI-Server` shows 11 secrets, all Apple/Windows
>    signing or store-API keys — **none scoped for cross-repo GitHub access** — and the default
>    `GITHUB_TOKEN` used elsewhere in this workflow is scoped to CI-Server only. Cloning the other repo
>    would need someone to mint a new PAT/deploy-key/GitHub-App-installation token with access to
>    `CI-Browser-Extension` and add it as a new CI-Server secret — an action in that repo's/org's
>    settings, not something this repo's CI config alone can grant itself.
> 2. **Even with that credential, `master` has no prebuilt Safari bundle to sync.** `git/trees/master` has
>    no `.output/` directory (it's gitignored build output); the only Safari-related in-tree file is
>    `store-assets/safari/app-icon-1024.png`. `package.json`'s `build:safari-mobile` script (`wxt build -b
>    safari --mv3`) has to actually run to produce `.output/safari-mv3`, so a clone-only step buys
>    nothing — the workflow would still need to `yarn install --immutable && yarn build:safari-mobile`
>    inside a second checkout, i.e. stand up an entire second JS toolchain (a separate lockfile, separate
>    node_modules) nested inside an iOS job that has never once run green against this script (it was
>    added 2026-08-20 in `d56fd656`; the last successful `mobile-build.yml` run predates it, 2026-08-13).
>
> **Concrete unblock, in the other repo:** publish a `v1.5.0` GitHub release (its `package.json` on
> `master` is already at `1.5.0`; `PINNED_VERSION` in `sync-safari-extension.sh` defaults to the same)
> with a `safari-mobile.zip` asset, built with the already-existing `npm run zip:safari-mobile` script in
> that repo. That satisfies the pinned-release fallback path CI-Server's script already implements, with
> no CI-Server change and no new cross-repo credential. See `sync-safari-extension.sh`'s header comment
> for the same finding inline with the code.

**(b) `CLiteRTLM.xcframework` has no x86_64 simulator slice.** Its `Info.plist` lists exactly two libraries: `ios-arm64` and `ios-arm64-simulator`. `mobile-build.yml` builds with `-destination 'generic/platform=iOS Simulator'`, which builds arm64 **and** x86_64:

```
ld: warning: ignoring file '…/CLiteRTLM.framework/CLiteRTLM':
    found architecture 'arm64', required architecture 'x86_64'
Undefined symbols for architecture x86_64: "_litert_lm_engine_create", …
```

Fix is either an arm64-only destination/`ARCHS`, or an xcframework that carries the x86_64 simulator slice.

With both worked around the app builds, installs, and launches correctly — so these are packaging/CI defects, not app defects.

### 6.3 P1 — a desktop build off any non-release commit can never start its stack

`frontend/apps/desktop/scripts/sync-compose-resources.cjs` resolves the image tag via `git describe --tags --exact-match`, falling back to `dev-<short-sha>`. On `15fde65c5` it emits **`dev-15fde65c5`** and exits 0 — no warning.

**No `dev-*` tag has ever been published**: querying the GHCR package `companion/api` returns **0 tags matching `^dev-`**. The newest published tag is `2026.8.23`. So the app builds happily and then fails at first launch when Docker cannot pull the images.

Corroborating evidence: a desktop stack was already running on this machine (7 containers, healthy, 11h uptime) — pinned to `ghcr.io/…/api:2026.8.23`, i.e. **220 commits behind this branch**. Desktop smoke-testing today validates the *shell*, not any feature in this review.

Before release sign-off, dispatch `publish.yml` and smoke desktop against a real tag. Until then, treat desktop results as shell-only and pass `CI_SERVER_IMAGE_TAG=2026.8.23` explicitly.

### 6.4 P1 — duplicate `FileService` provider breaks the activity rollup

The seed logs, non-fatally:

```
ERROR: Failed to refresh activity rollup source files
  TypeError: fileService.aggregateHourlyActivity is not a function
```

Two different exported classes are both named `FileService`:

- `domains/files/services/FileService.ts` — **has** `aggregateHourlyActivity` (line 718)
- `domains/memory/services/FileService.ts` — **does not**

`ActivityModule` (`domains/activity/index.ts`) imports **both** `FilesModule` and `MemoryModule`, and both barrels provide *and export* their own `FileService` (`files/index.ts:47`, `memory/index.ts:207`). `ActivityRollupService` imports the `files` one by type, but at runtime resolves the `memory` one, so the `files` rollup source silently produces nothing.

This is invisible to `ActivityRollupService.test.ts`, which stubs every provider as `{ aggregateHourlyActivity: … }` — a test that cannot fail for the reason the code is broken.

### 6.4b P1 — `OllamaService` injects without its methods, same family as §6.4

The `SmartRotationAnswerInferCron` cron fails on every run:

```
ERROR [Cron] Scheduled job SmartRotationAnswerInferCron.run failed
TypeError: this.ollamaService.chat is not a function
  at AnswerInferenceListener.inferAnswerForQuestion (…/smart-rotation/listeners/AnswerInferenceListener.ts:309)
```

Unlike §6.4 this is **not** a duplicate-class collision — there is exactly one
`OllamaService` (`domains/llm/services/OllamaService.ts:235`) and `chat` is
genuinely its method (line 661). The wiring also looks right on paper:
`LlmCoreModule` provides and exports it, `LLMModule` re-exports `LlmCoreModule`,
and `SmartRotationModule` imports `LLMModule`. Yet at runtime the injected object
lacks the method.

The likely mechanism is a **barrel import cycle**: `AnswerInferenceListener:32`
imports `OllamaService` from the `@ci/domains/llm` barrel, whose `LLMModule`
pulls in a long chain (`MemoryModule`, `IntelligenceModule`, `ToolsModule`, …).
If `smart-rotation` is reachable from that chain, the barrel is half-evaluated
when the listener is loaded and the class reference is not yet the class. The
module already carries a comment about exactly this hazard
(`domains/smart-rotation/index.ts:10`). Importing from the concrete path
(`domains/llm/core.module` or the service file) rather than the barrel is the
usual fix, but confirm the cycle first.

**Why no test caught it:** `AnswerInferenceListener.test.ts` passes — it supplies
its own `ollamaService` double. Same blind spot as §6.4: when a service's job is
*wiring*, a suite that stubs every collaborator cannot fail for the reason the
code is broken.

Found while re-seeding, not by any suite.

### 6.5 P2 — a local iOS build makes `yarn lint` unusable

`frontend/apps/ios/scripts/sync-safari-extension.sh` fills
`ios/App/SafariWebExtension/Resources/` with bundled JS from CI-Browser-Extension.
That directory is gitignored (`frontend/apps/ios/.gitignore:13`), but **ESLint does
not read `.gitignore`**, so the root `yarn lint` walked five vendored bundles and
reported **7,989 errors** — none of them in this repo's source. CI never sees it,
because CI lints a fresh checkout that has never run the sync. Fixed here by adding
the path to `eslint.config.mjs`'s `ignores`, alongside the entries already there for
exactly this reason.

### 6.6 P2 — the committed Capacitor generated files are stale

Running `yarn cap sync` on either mobile app produces a diff against what is
committed. On Android, `capacitor.settings.gradle` and `app/capacitor.build.gradle`
gain `capacitor-community-background-geolocation` and `capacitor-community-sqlite`;

already declared dependencies, so the checked-in generated files simply lag the
declared plugin set.

Nothing broke because of it — the builds regenerate these before compiling — but it
means every developer who syncs gets an unrelated diff in their working tree, and it
invites someone to commit or revert it at random. Decide whether these files should
be committed at all; if they should, regenerate and commit them once.

### 7.1 The new nav-shell spec, and proof it is not vacuous

`tests/e2e/nav-shell.spec.ts` covers what the `layouts/Main/**` unit tests cannot: that a rail row points at a route that really renders, that the two nav surfaces generated from one source really do agree in a running app, and that **the way out of the app still exists**.

It was verified by re-introducing the exact regression `railDestinations.ts` documents — gating the Self tile on a flag that ships `false`:

```diff
-{ id: 'self', to: '/self', … flag: 'self.page', end: false }
+{ id: 'self', to: '/self', … flag: 'forecast.page', end: false }
```

Result: **exactly one test failed** — `the Self tile still carries Log out, and logging out works`, with `Error: the shell has no Log out control` — and the other five stayed green. Reverted afterwards; `git diff` on that file is empty.

## 8. Reproducing this baseline

```bash
export PATH="$HOME/.asdf/shims:$PATH"
export JAVA_HOME="$(brew --prefix openjdk@21)/libexec/openjdk.jdk/Contents/Home"
export ANDROID_HOME="$HOME/Library/Android/sdk"

```

Then the suites in §2/§3, and for §4 bring up **three** services, not two:

```bash
docker compose -f docker-compose.yml -f docker-compose.local.yml --profile local up -d database setup-database object-store hbpe-service
```

`hbpe-service` has no host port mapping in the committed compose files; add `ports: ["8002:8002"]` via an override so the host-run seed can reach `HBPE_HOST`.

> ⚠️ The stack binds host `5432` and `9000`. Check no sibling worktree stack is live (`make urls`, `docker ps`) before migrating, or a neighbour's schema ends up in your baseline.
