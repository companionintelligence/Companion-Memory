01The verdict

Mostly no — and the number everyone quotes is wrong. LifeScope's docs describe seven core data objects, but the codebase shipped 20 MongoDB collections. Against that, 63 tables is a 3.2× expansion over eight years, during which the product gained local LLM inference, RAG over a vector store, behavioural forecasting, background jobs, object storage and paired-device sync. That is a normal amount of growth for the amount of new capability.

The width numbers say the same thing. 46 of 63 tables are under 20 columns. Only two are past 40. ci.content is 16 columns against LifeScope's 15 — it never drifted at all.

Where the fear is justified is coherence, not size. LifeScope had one Events collection and one type word; today user actions land in six sibling tables that share no key, no time column and no type vocabulary, so "what happened Tuesday" is a six-way fan-out merged in TypeScript. Three separate entity-type vocabularies exist in the TypeScript, with a bridging map whose own comment admits they "only partially overlap". Eight TypeORM classes map ci.entities and none covers all 22 columns.

The repetition that follows is the real cost: (source_type, source_system, source_id) re-declared on eleven tables with five or six different scoping rules — one of which, on ci.events, is a live cross-tenant data-loss path.

None of this argues for a rewrite. It argues for one vocabulary, one tenancy column, one coordinate representation, and deleting what is provably dead. The ranked list is in §09.

10Accidental complexity, ranked

Findings from a four-lens audit of the migrations and entity code, each then handed to an independent agent told to refute it. Six of the sixteen original findings did not survive that pass and are not listed. The ones below are the corrected, narrowed versions.

HighA live cross-tenant data-loss path in ci.events

events_source_triple_uniq is global while every other provenance rule in the schema is user-scoped, and ci.events.user_id is NOT NULL. bulkInsertIdempotent scopes its pre-check by user but emits an ON CONFLICT arbiter that is not user-scoped — so a second user re-ingesting a triple another user already holds has their row silently swallowed by DO NOTHING, gets the unpersisted entity echoed back as if stored, and has ci.capture_events.materialized_id stamped with an event_id that does not exist.

Fix: rebuild as (user_id, source_type, source_system, source_id) WHERE source_id IS NOT NULL and update the arbiter in EventService.createManyBatched to match. This is already noted in two in-repo comments; it just hasn't been done.

HighSix timeline tables, no shared key

User actions are split across ci.events, ci.communications, ci.browser_activity, ci.position, ci.user_snapshots and ci.capture_events with no shared key, no shared time column and no shared type vocabulary — so search hydration batches 14 ways and cross-timeline paging is not expressible in SQL.

Narrowed by the refutation pass: ci.events is genuinely the hub for five other tables. The problem is the five sibling timelines beside it, not an absence of any hub.

LifeScope didOne Events collection with datetime + type from a closed list, plus foreign keys to contact / content / location.
HighEvent → Content lost its foreign key

20250925145800_replace_events_table.sql dropped the old events table CASCADE, which silently took ci.content.event_id's FK with it. No migration since restores it, so the column is an orphanable uuid — while four sibling tables do carry real FKs to ci.events(event_id). The API exposes no downward traversal either, which is why HBPE's data_client.py documents that it must use raw SQL.

Fix: orphan-nulling sweep, then add the FK; expose an event → contents connection. The covering index already exists.

11Essential complexity — leave it alone

Over-correcting toward seven tables would break real things. These earn their keep:

  • The 8 hbpe.* tables. A separate Python sidecar reads them directly. They are a published interface, not internal structure.
  • ci_search.embeddings + ci_search.vectors. pgvector and tsvector in polymorphic side tables is the right shape — it keeps 768-dimension vectors off the hot core tables. Consolidating the inline vector columns into these was a good call.
  • The three TimescaleDB hypertables (position, communications, user_snapshots). High-volume time series with genuinely different retention needs from event rows.
  • Location vs Place. LifeScope deferred this and was worse for it. A GPS fix and a named place are different objects; splitting them was correct. Only the three-representations-of-coordinates part is accidental.
  • Device and pairing tables. LifeScope was a hosted web app. This is an appliance with paired clients — that is new, real surface area.
  • ci.entities as a polymorphic node table. The idea is sound and it is what makes a graph traversable across nouns. The problem is the eight competing classes over it, not the table.

What the agents refused to do

Three of my earlier recommendations were measured and rejected. Each rejection is more valuable than the change would have been:

  • Don't fold ci.browser_activity into ci.events. Measured; the fold doesn't pay for itself. This reverses §12 of the earlier plan.
  • Don't side-table the ci.events analytics block — just drop the dead columns outright.
  • Don't split ci.inventory. Its 53 columns look like three concepts but the seams don't hold under measurement.
  • Don't build one class over ci.entities. The 25 toEgressType sites are 7 Person / 7 Concept / 5 Place / 3 Node with mutually exclusive @AfterLoad bodies. TypeORM allows one per class, so a merged class needs an entity_type switch — reinstating the polymorphism the merge was meant to delete. Keep the per-type classes; fix their column typings.

Constraints discovered by execution

These came out of actually running the migrations, not reading them:

  • Postgres enums can't be edited and used in one transaction. ALTER TYPE … ADD VALUE then UPDATE in the same migration → unsafe use of new value. dbmate wraps every migration in a transaction, so the plan drops enums and never adds one.
  • DROP COLUMN reclaims zero bytes. Measured at 300k rows: 57,155,584 B before and after, even with VACUUM ANALYZE. Only VACUUM FULL recovered it (50,159,616 B) — and that must not go in a migration. Every size claim here is about future rows.
  • NOT VALID CHECKs still fire on UPDATE. They skip the initial scan; they don't exempt existing rows from future writes. A surviving out-of-list row becomes permanently un-updatable.
  • Never gate a migration on emptiness with RAISE EXCEPTION — it aborts dbmate migrate on exactly the appliances that have the data, stranding them mid-version. Use RAISE NOTICE.
